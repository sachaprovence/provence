## 4. CRM : prospects, contacts, entreprises, biens, tags, Kanban

- **Prérequis** : organisation existante avec données seedées.
- **Étapes** : couvert par `tests/crm/*.test.ts` (Lead/Contact/Company/Property/Attachment/Tag, CRUD complet + isolation par organisation + cascades Prisma), et par le parcours `golden-path.mjs` (connexion → tableau de bord → liste filtrée de prospects → fiche prospect → analyse IA → score).
- **Résultat attendu** : CRUD complet fonctionnel, aucune régression depuis `v1.1` (aucun changement de code métier CRM dans `v1.2`, périmètre volontairement non fonctionnel).
- **Preuve conservée** : 803 tests `vitest` (dont `tests/crm/*.test.ts`, `tests/tenant-isolation/leads.test.ts`) tous passés à chaque commit de `v1.2` (voir chaque rapport de validation AR-0163 à AR-0170).
- **Résultat observé** : ✅ conforme pour la couche testée automatiquement. **Nuance sur `golden-path.mjs`** : ce script échoue actuellement dans cet environnement de développement à l'étape "liste des prospects qualifiés" — **cause identifiée avec certitude, pas une régression `v1.2`** : `golden-path.mjs` filtre `?stage=QUALIFIED` et fait progresser le prospect trouvé dans le pipeline au fil de son exécution ; la base de développement partagée de cette session a été réutilisée pendant un très grand nombre d'exécutions (`v1.1` puis `v1.2`, seed jamais réinitialisé) et ne contient donc plus aucun prospect au stade `QUALIFIED` pour le compte administrateur de démonstration (vérifié directement en base : 0 ligne `Lead` à ce stade pour cette organisation). Ce script suppose implicitement un jeu de données fraîchement seedé à chaque exécution — exactement ce que fait `.github/workflows/e2e.yml` (service PostgreSQL éphémère, seed unique, une seule exécution), donc ce mode d'échec n'affecte pas le signal CI réel. Non corrigé ici (modifier `golden-path.mjs` serait hors périmètre de `v1.2`, qui n'ajoute aucune fonctionnalité métier) — documenté pour qu'un futur opérateur de cette session de développement sache pourquoi une réexécution locale peut échouer sans que le code soit en cause.

## 16. Intégrations nécessitant encore un compte/sandbox réel

Conformément à la contrainte "ne jamais déclarer une intégration tierce
validée sans compte réel ou sandbox officiel", les intégrations suivantes
restent **non validées en conditions réelles** dans cette recette (testées
uniquement contre des serveurs HTTP locaux simulant fidèlement le
protocole de l'API réelle — SigV4 pour S3, REST+Basic Auth pour Twilio,
OAuth2 pour Gmail/Outlook, webhook signé pour Stripe) :

- **Stripe** (facturation réelle) — `BILLING_PROVIDER=demo` utilisé pour
  toute cette recette, conformément à `AR-0027` (aucun paiement client
  final).
- **Twilio** (SMS/WhatsApp/Téléphone réels) — jamais testé contre un
  compte Twilio réel.
- **Gmail/Outlook** (envoi d'email réel) — jamais testé contre un compte
  Google/Microsoft réel.
- **S3** (stockage réel, AWS ou compatible) — jamais testé contre un
  bucket réel.

Ces quatre intégrations nécessitent un compte réel (ou sandbox officiel)
et une validation dédiée avant l'onboarding d'un premier client
utilisant l'une d'elles.
